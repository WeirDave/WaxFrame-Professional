4. Fixture-based regression test for provider response-shape drift
   ─────────────────────────────────────────────────────────
   WHAT:   A standalone, node-runnable test (no live API calls)
           that feeds canned multi-block/multi-part response
           JSON — including an extended-thinking-shaped
           Anthropic payload (thinking block at index 0, text
           block after) and a thought-part-shaped Gemini
           payload (thought:true part before the real part) —
           through WFProviderCatalog.extractAnthropicText() /
           .extractGeminiText() and asserts the correct text
           comes out, not ''.
   WHY:    v3.63.410 fixed a live bug where Claude's extended-
           thinking responses were misread as empty because
           every Anthropic extractor hardcoded content[0].text.
           Nothing in WaxFrame changed to cause this — Anthropic
           started returning a leading thinking block server-
           side with zero notice. The exact same class of drift
           is plausible for Gemini (thought:true parts) and, in
           principle, any provider whose response shape isn't a
           flat single value. A fixture test converts "we found
           out live, mid-demo, from a customer-facing error
           modal" into "release-check catches it before ship."
           Provider-catalog.js's extractors are plain functions
           now (v3.63.410's firstAnthropicTextBlock /
           firstGeminiTextPart), so they're testable in
           isolation without a browser or a live key.
   STATE:  OPEN — not started. Natural fit as the first flow
           under the proposed tools/flow-check.mjs harness (see
           entry below / CLAUDE.md §8-C), but doesn't need to
           wait for that full E2E rig — a standalone
           tools/test-provider-extractors.mjs that requires
           provider-catalog.js's IIFE and reads
           WFProviderCatalog off the resulting global would
           work today and could optionally be wired into
           release-check.mjs as an additional check later.
   WHERE:  js/provider-catalog.js — firstAnthropicTextBlock()
           and firstGeminiTextPart() (~line 186-205),
           WFProviderCatalog.extractAnthropicText /
           .extractGeminiText exports (~line 685).
   DONE:   A node-runnable test file exists with fixtures for:
           (a) plain single-block Anthropic response, (b)
           thinking-block-then-text Anthropic response, (c)
           thinking-only Anthropic response (genuinely empty —
           should still report empty, not throw), (d)-(f) the
           same three shapes for Gemini using thought:true, (g)-
           (i) the same three for OpenAI using firstOpenAIMessage
           (plain content, refusal-only, empty choices array) —
           added to scope v3.63.414 after the OpenAI-format twin
           of this exact bug was found in a full-codebase audit.
           All nine assert the extractor returns the expected
           string. Documented in README or a comment how to run
           it (`node tools/test-provider-extractors.mjs`).


5. Release ceremony has two steps with no automated verification they ran
   ─────────────────────────────────────────────────────────
   WHAT:   Two CLAUDE.md-documented release-ceremony steps —
           "create the GitHub release immediately, every single
           time" (§5 item 9) and "run node tools/indexnow-
           ping.mjs" (§5 item 10) — are both purely procedural.
           Nothing checks that HEAD on main has a matching
           vX.Y.Z GitHub release/tag, and indexnow-ping.mjs's
           success or failure isn't logged or verified anywhere
           after the fact.
   WHY:    Item 9 has already failed once for real: v3.63.408
           shipped its commit with no matching GitHub release,
           caught only because someone happened to run `gh
           release list`. The live site (GitHub Pages serving
           main directly) shows zero symptom when either step is
           skipped, so detection is accidental, not systematic.
           indexnow-ping's failure mode is worse — even a run
           that WAS attempted just prints an HTTP status to
           stdout with nothing persisted, so "skipped" and
           "attempted but failed silently" look identical after
           the fact, compounding a project that's already
           SEO-index-starved (CLAUDE.md §8B).
   STATE:  OPEN — not started. Design correction from the first
           pass at this: a check added to release-check.mjs
           (push-triggered, synchronous) CANNOT correctly catch
           "the tag/release step got skipped" — by the ceremony's
           own design, the tag is created AFTER the commit is
           pushed, so a synchronous check would false-positive on
           every single normal release (it'd see "no tag yet"
           during the completely normal in-progress window,
           before step 9 has had a chance to run). A real
           implementation needs to run on a DELAY — a scheduled
           GitHub Action (daily, or the pricing Worker's own
           daily-cron pattern) checking "is the newest CHANGELOG
           entry's version tag more than N hours old and still
           missing" — not a check wired into the push-triggered
           gate. Caught before shipping the wrong version of this
           (v3.63.415's CHANGELOG has the reasoning).
   WHERE:  A NEW scheduled workflow (e.g.
           .github/workflows/release-tag-check.yml, on: schedule)
           would own the tag-staleness check; tools/indexnow-
           ping.mjs still needs a persisted result (a repo file,
           a KV entry — anywhere with history) instead of only
           ever printing to a terminal nobody's watching.
   DONE:   A scheduled (not push-triggered) check verifies
           CHANGELOG.md's newest "## vX.Y.Z" entry has a matching
           git tag once enough time has passed for the ceremony to
           reasonably have completed, and surfaces somewhere
           visible (a failed scheduled Action run, a `gh issue
           create`, etc.) if not. indexnow-ping.mjs logs its
           result somewhere checkable instead of only stdout.

NOTES ON FORMAT
════════════════════════════════════════════════════════════
Every entry above uses the same five-field structure:
WHAT, WHY, STATE, WHERE, DONE. Going forward, any new
backlog entry MUST follow that structure so the document
stays pickup-ready for any reader.

State vocabulary:
  OPEN      — known and ready to work on; no blockers.
  PARTIAL   — work has started, more remains; current
              state described in the entry.
  PARKED    — design is understood but not on a near-term
              release path; revisit later.
  DEFERRED  — paused waiting on an external input
              (user repro, upstream decision, etc.).

When an item ships, it moves to CHANGELOG.md and is
DELETED from this file. No "CLOSED" section here — the
changelog is the system of record for completed work.
