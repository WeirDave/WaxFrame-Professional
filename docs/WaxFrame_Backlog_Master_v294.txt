  %%CONFLICTS_START%% block, truncate mid-document, or hallucinate
  formatting that breaks the parser. The filter list currently
  holds Jamba (added v3.63.132) and a few others. PRACTICE: when a
  new family proves structurally incompatible as Builder in two
  consecutive measured runs, add it to the list, exclude it from
  Builder recommendations, and badge it Reviewer-only in the
  picker. No candidate is queued; this is a habit, not a task.

  v280 file's history. Do not build preemptively.

• THREE DUPLICATE-LOGIC CLEANUPS (old #6). PARKED 2026-08-01. All
  three already carry "mirror of" comments pointing at their
  counterparts, which is the cheap half of the fix. Consolidation
  is a refactor with no user-visible payoff; revisit only if one
  of the pairs actually drifts.

• CLOUDFLARE AI-CRAWLER CONTROLS DO NOT APPLY (added v286,
  2026-09-19). Cloudflare emailed about migrating "Block AI Bots"
  to separate Search / Training / Agent controls. It is a no-op
  for waxframe.com: the zone is on Cloudflare DNS
  (drake/cass.ns.cloudflare.com) but DNS-only, grey cloud — the A
  records point straight at GitHub Pages (185.199.108-111.153)
  and a live HEAD on /robots.txt returns Server: GitHub.com with
  Fastly headers and no cf-ray. Crawler controls are enforced at
  the Cloudflare proxy, which this traffic never touches.
  robots.txt is served by GitHub from the repo root and is
  User-agent: * / Allow: / — unchanged and correct.
  PRACTICE: if the orange cloud is ever turned on for
  waxframe.com (caching, analytics, hiding the Pages origin),
  set all three controls to Allow BEFORE proxying, not after.
  The migrated defaults are Search: Allow / Training: Disallow AI
  Training / Agent: Block on pages with ads. "Disallow AI
  Training" is the wrong setting here — there is no content
  business to protect and being in training corpora is exactly
  how the brand collision with physical wax frames gets beaten
  (see SEO campaign context, CLAUDE.md §8B). The Agent default
  is harmless: no ads on the site. Workers (claude-proxy,
  pricing-worker) are unaffected either way — crawler controls
  are a zone-level content feature.

• CHECK 8 CANNOT SEE JS-GENERATED HANDLERS (old #9). Check 8's
  inline-handler regex scans .html only, so an on*= written into a
  JS template literal and injected via innerHTML would ship,
  be blocked by CSP at runtime, and pass the gate. This is a
  TOOLING GAP, not a defect: js/ was swept manually in v3.63.488

  storage.js:741 reading getAttribute('onclick') in the XSS

  known; extend INLINE_HANDLER_RE's file scope if a regression
  ever appears.

NOTES ON FORMAT
════════════════════════════════════════════════════════════
Every numbered entry above uses the same five-field structure:
WHAT, WHY, STATE, WHERE, DONE. Going forward, any new
backlog entry MUST follow that structure so the document
stays pickup-ready for any reader.

State vocabulary:
  OPEN      — known and ready to work on; no blockers.
  PARTIAL   — work has started, more remains; current
              state described in the entry.
  PARKED    — design is understood but not on a near-term
              release path; revisit later.
  DEFERRED  — paused waiting on an external input
              (user repro, upstream decision, etc.).

When an item ships, it moves to CHANGELOG.md and is
DELETED from this file. No "CLOSED" section here — the
changelog is the system of record for completed work.

Two habits this document keeps failing at, both fixed in v281:
  • Shipped items must be DELETED the day they ship. Old #7 sat
    here marked SHIPPED for over a month.
  • Decisions and standing practice do not belong in a numbered
    queue — they inflate the count and can never be closed.
    Put them in STANDING PRACTICE.
